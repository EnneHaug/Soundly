    **Why source-regex tests on `sw.ts` / `vite.config.ts`** (RESEARCH Finding 9):
    - `sw.ts` runs in `ServiceWorkerGlobalScope` which jsdom does NOT emulate. Importing it would throw "self is not defined".
    - `vite.config.ts` is consumed by Vite's config loader, not by the test runner. Importing it would require resolving the build-time deps (`@vitejs/plugin-react`, etc.) — heavyweight for a one-line assertion.
    - Regex-on-source has low signal but high specificity: catches accidental removal of the locked phrases during future refactors. Cheap insurance.

    **Why DOMParser for sitemap.xml** — the vitest env is jsdom (verified `vitest.config.ts:7`), so `DOMParser` is global. This catches malformed XML that a naive regex would miss (e.g., unclosed tags).

    **Why no test for `docs/deploy-runbook.md`** — it's a human-read doc; Plan 05's own verifier already asserts content presence. Adding a test here would be circular.

    **Why no test for `scripts/generate-og-image.mjs`** — running the generator is itself a verification (Plan 04 Task 3); the test asserts the OUTPUT exists + is correct size + is a PNG.

    **Why no `package.json` test** — the JSON file has a typed contract (npm tooling enforces shape); the only edit (`og-image` script entry) is verified by Plan 04 Task 2.

    **No mocking** — every test reads real files synchronously. No fakes, no spies. Fast, deterministic, debuggable.
