# Phase 11 — UI Design Contract

> Visual and interaction contract for the **hand-authored static marketing landing**
> (`index.html` at repo root, post-split). Covers hero, install CTA states, inline
> product screenshot, FAQ, iOS honesty section, footer, plus the platform-detection
> JS that swaps install affordances. Generated by gsd-ui-researcher; will be
> verified by gsd-ui-checker.

**Inheritance posture.** Phase 11 inherits the **warm-earth palette** verbatim from
`src/index.css` `@theme` — the landing reuses the same CSS variable values (duplicated
into an inline `<style>` block per RESEARCH Finding 12), so a visitor who lands on
`/Soundly/` and clicks through to `/Soundly/app/` experiences zero color or typography
discontinuity. Critically, the landing **does NOT load Tailwind** — every class string
established in Phases 3–9 is irrelevant here; the contract below specifies raw CSS
values directly. Every visual decision traces to a CONTEXT D-LAND-01..16 locked
decision, a RESEARCH finding, or an explicit Claude's Discretion call-out.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (hand-authored static HTML + inline `<style>` block) |
| Preset | not applicable |
| Component library | none (no React on landing per LAND-01) |
| Icon library | none (Unicode glyphs only: `▸` / `▾` for `<details>` marker, `✓` for install confirmation, `·` middle dot in footer) |
| Font | system stack — `system-ui, -apple-system, "Segoe UI", Roboto, sans-serif` (zero-network-cost; matches Tailwind v4 default sans inherited by the app shell) |
| Modal primitive | none — no modal on landing |
| Disclosure primitive | native `<details>` / `<summary>` (RESEARCH Finding 8 — Baseline Widely Available since Jan 2020, no ARIA needed) |
| CSS strategy | inline `<style>` block in `index.html` (RESEARCH Finding 12) — target ≤ 3 KB |
| Dark mode | `@media (prefers-color-scheme: dark)` swap of palette variables — matches the app's convention (D-LAND Discretion) |

**Why no Tailwind on landing.** The landing has zero React runtime per LAND-01. Loading
Tailwind would either (a) duplicate the app's CSS bundle into a second entry — wasted
bandwidth and broken hash-stability, or (b) couple the landing to the app bundle's
build hash — landing breaks on any app rebuild. The 30–50 lines of hand-rolled CSS
needed for the compact one-page layout fit cleanly in an inline `<style>` block
(Finding 12 recommendation).

**Why no third-party registry.** No shadcn, no headless-UI, no animation lib. The
landing is two interactive elements (`<button id="install-btn">` and
`<details id="ios-install-panel">`) plus three semantic regions
(`<header>`/`<main>`/`<footer>`). Adding a registry would be design-system overreach.

- Hero `<h1>` margin = **1rem 0 1.5rem** — asymmetric to pull the value paragraph

## Typography

Type scale (5 roles — minimal because landing is content-light):

| Role | Size | Weight | Line Height | Selector |
|------|------|--------|-------------|----------|
| `h1` (hero) | `clamp(1.75rem, 5vw, 2.75rem)` — fluid 28px → 44px | 600 (semibold) | 1.2 | `.hero h1` |
| `h2` (section heading: "Questions", "If you're on iPhone") | `1.5rem` / 24px | 600 (semibold) | 1.3 | `main h2` |
| `h3` (FAQ question) | `1.125rem` / 18px | 600 (semibold) | 1.3 | `.faq h3` |
| Body / paragraph | `1rem` / 16px | 400 (regular) | 1.6 (generous for reading) | `body`, `p` (default) |
| Footer + microcopy | `0.875rem` / 14px | 400 (regular) | 1.5 | `footer`, `#install-confirm`, `.install-cta-helper` |

**Font weight palette: exactly 2 weights** — `400` (regular) for body / paragraphs /
footer / install confirmation, `600` (semibold) for all headings and the install
button label. No `700` (bold), no `300` (light) — keeps the calm typographic tone
consistent with the app's `font-semibold` headings.

**Font family:**
```css
font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif;
```
Declared on `body`; cascades to all descendants. Matches Tailwind v4 default `font-sans` (the app shell's body font), so visual transition from landing → app is seamless.

**Numeric handling:** Not applicable (no countdowns, no live numeric values on landing
— `font-variant-numeric: tabular-nums` is NOT needed here).

**Hero `<h1>` precision contract:**
- Verbatim text per D-LAND-01: **"A calmer alarm that alerts you gently"** — no
  changes, no localization, no abbreviation
- Display em-dashes (—) as literal U+2014, never `--`
- The em-dash usage on the landing follows the **Phase 10 OG image precedent** (the
  `<title>` is `Soundly — a calmer alarm that alerts you gently` — same em-dash
  glyph)

1. `#install-confirm` text color (`Installed ✓ — launching app…`) — the only place

   page lifecycle

Accent is **NOT** used for:
- Install button background (uses sage — primary action)
- Open Soundly link background (uses sage — primary action)

Composer's Start button (the single high-stakes "this will run an alarm" affordance).
The landing has no equivalent stakes — the install button doesn't fire an alarm, it
opens a browser-native prompt. Reserving accent for the **post-install confirmation
moment** preserves the visual language: accent always means "something irreversible /
celebratory just happened." [Claude's Discretion — locked here]

**Destructive color:** Not applicable. The landing has zero destructive actions.

**FAQ Draft Copy (6 questions — planner may add up to 2 more from the D-LAND-03
candidate list if scope allows; otherwise this is the verbatim contract):**

1. **Will Soundly actually wake me up?**
   Yes — if you use it the way it's designed. The first phase plays soft sounds; the
   second adds vibration on devices that support it; the third ramps to full volume.
   The escalation is the safety net. For deep sleepers, keep the device near you and
   the screen on. (iPhone has limitations — see below.)

2. **Does it work offline?**
   Yes. Once installed, Soundly runs entirely on your device — no server calls during
   an alarm. The landing page is online; the app itself is offline-capable.

3. **How much does it cost?**
   Nothing. Soundly is free and has no ads, no accounts, no tracking. It will not
   start charging later.

4. **Where's my data?**
   Nowhere — Soundly stores no settings between sessions and sends nothing to a
   server. Custom alarms can be shared via link (which encodes the alarm into the URL
   itself); the link is the only "storage."

5. **Can I customize the alarm sounds and timing?**
   Yes. The Custom composer lets you stack any number of segments, pick a sound per
   segment (gentle chime, triangle ping, or full alarm), and set the duration of each.

6. **Why is there no sign-in?**
   By design. Soundly is meant to be the simplest possible alarm — install, set,
   sleep. No accounts to recover, no email to confirm, no profile to maintain.

**Empty state / error state / destructive copy:** Not applicable on landing. The
landing has no data dependencies (nothing to be "empty"), no failure modes (no
network calls during a visit), and no destructive actions.

**Locale:** English only per CONTEXT Deferred Ideas. The `<html lang="en">` attribute
is mandatory (Lighthouse SEO checks for it).

### 1. Install button (`#install-btn`) — Android / desktop Chromium only

| State | Visual | Interaction |
|-------|--------|-------------|
| **Hidden (default)** | `hidden` attribute set; CSS `[hidden] { display: none !important; }` enforces invisibility even if a style overrides | Element exists in DOM but is unreachable by tab; ARIA-hidden by virtue of `hidden` attribute |
| **Visible (post-`beforeinstallprompt`)** | Sage background (`#5c6b56`), white-ish text (`#f4f1eb`), 0.5rem border-radius, 0.85rem 1.5rem padding, semibold 600 weight, 16px font-size | `cursor: pointer`; tab-focusable |

| **Focus-visible** | `outline: 2px solid #5c6b56; outline-offset: 2px` (sage ring at 2px) | Only on keyboard focus; not on mouse click |

### 2. iOS `<details>` install panel — iOS Safari only

| State | Visual | Interaction |
|-------|--------|-------------|
| **Hidden (default, non-iOS)** | `hidden` attribute set; element doesn't render | Unreachable |
| **Closed (iOS visitor, panel collapsed)** | `<summary>` shows "Install on iPhone" prefixed by custom marker glyph `▸` (right-pointing triangle, U+25B8); border `1px solid #d4cbbe`; border-radius `0.5rem`; padding `0.75rem 1rem`; max-width `560px`; centered | Tab focusable; Space/Enter toggles open; default `<details>` keyboard semantics |
| **Open** | `<summary>` marker rotates 90° to `▾` (down-pointing triangle, U+25BE) via CSS `details[open] summary::before { transform: rotate(90deg); }`; panel body slides into view (browser-native — no JS animation); ordered list `<ol>` with 3 steps, each step has one `<strong>` glyph reference | Same keyboard semantics |

**Custom marker implementation (per RESEARCH Pitfall D — both browser quirks
covered):**

```css
/* Hide native disclosure marker — both vendor prefixes */
summary::-webkit-details-marker { display: none; }
summary::marker { content: ''; }

/* Custom marker glyph — pseudo-element, rotates on [open] */
summary {
  list-style: none;          /* Firefox marker suppression */
  display: flex;
  align-items: center;
  gap: 0.5rem;
}
summary::before {
  content: '▸';              /* U+25B8 BLACK RIGHT-POINTING SMALL TRIANGLE */
  display: inline-block;
  transition: transform 200ms ease-out;
  color: #5c6b56;            /* sage */
}
details[open] > summary::before {
  transform: rotate(90deg);
}

/* prefers-reduced-motion gate — instant rotation */
@media (prefers-reduced-motion: reduce) {
  summary::before { transition: none; }
}
```

## Accessibility Contract

**Mandatory WCAG 2.1 AA conformance items:**

1. **Landmarks (SC 1.3.1, 2.4.1):** Single `<header>` (hero), single `<main>`, single
   `<footer>` — semantic HTML5 elements with implicit ARIA roles. No `role=` attributes
   added.

2. **Heading hierarchy (SC 1.3.1, 2.4.6):**
   - One `<h1>` per page (hero)
   - `<h2>` for each main section (`Questions`, `If you're on iPhone`)
   - `<h3>` for each FAQ question
   - **NO `<h2>` skipped to `<h4>`** — strict hierarchy

3. **Document language (Lighthouse SEO):** `<html lang="en">` mandatory.

4. **Page title (SC 2.4.2):** `<title>Soundly — a calmer alarm that alerts you gently</title>`
   — distinct from app shell title.

5. **Color contrast (SC 1.4.3, 1.4.11):** Verified in the Color table above. All
   text+background pairings meet AA in BOTH light and dark modes. Focus rings meet
   non-text contrast (3:1) against both surfaces.

6. **Focus visibility (SC 2.4.7):** Every interactive element has a `:focus-visible`
   ring (sage in light, lifted-sage in dark). No element relies on color alone to
   convey focus — the outline + offset ensures shape-based discrimination.

7. **Keyboard navigation (SC 2.1.1):**
   - Tab order matches document order: `#install-btn` (if visible) → `<details>` summary
     (if visible) → `.open-app-link` → footer GitHub link
   - `<details>` native keyboard semantics: Tab to focus summary, Space/Enter to toggle
   - No `tabindex` values > 0 (would break natural order)
   - No keyboard traps

8. **Touch targets (SC 2.5.5):** All interactive elements ≥ 44×44px (button padding,
   summary padding, anchor padding chosen to satisfy this). Documented per element
   in the Spacing section.

9. **Reduced motion (SC 2.3.3):** `@media (prefers-reduced-motion: reduce)` collapses
   all transitions/animations to 0.01ms (effectively instant) — covers the `<details>`
   marker rotation, the install button hover transition, and any other animated
   property.

10. **Screen reader contract:**

| Element | SR announcement |
|---------|-----------------|
| Hero `<img src="og-image-v1.png">` | `alt="Soundly — a calmer alarm"` — describes the ring + wordmark visual |
| Screenshot `<img src="screenshot-composer-v1.png">` | `alt="Soundly Composer with Wake Easy preset open, showing five segments — four 4-minute gentle chime segments followed by a 1-minute alarm segment"` — describes the screenshot's purpose, NOT pixels |
| `#install-btn` | Default: button label "Install Soundly" — sufficient because the button is hidden until installable; no extra `aria-label` needed |
| `<summary>Install on iPhone</summary>` | Native `<details>` semantics — SR announces "Install on iPhone, collapsed" / "Install on iPhone, expanded"; no ARIA needed (RESEARCH Finding 8) |
| `.open-app-link` (`<a href="/app/">Open Soundly</a>`) | Link text "Open Soundly" — sufficient |
| `#install-confirm` text | Wrapped in a region with `aria-live="polite"` (set on the `.install-cta` container) so the appearance is announced when it un-hides; SR reads "Installed, launching app" (the `✓` U+2713 is decorative — wrap it in `<span aria-hidden="true">✓</span>` to suppress the literal "check mark" announcement) |
| Footer GitHub link | Link text "GitHub" — context implied by surrounding " · Made by J. B. E. Haug · © 2026"; sufficient for the compact footer |

11. **`aria-live` region for install confirmation:**
    ```html
    <div class="install-cta" id="install-cta" aria-live="polite" aria-atomic="false">
      <!-- children here -->
    </div>
    ```
    Why `polite` not `assertive`: the confirmation is a passive success notice, not an
    interrupt. `assertive` would cut off whatever the user was hearing — too aggressive
    for a calm landing.

12. **Image fallback for hero (if og-image fails to load):** The `<h1>` text below the
    hero image carries the brand message — even with `<img>` broken, the page makes
    sense. No CSS background-image dependency on the hero visual.

13. **No flashing content (SC 2.3.1):** No CSS animations exceed the 3-flash-per-second
    threshold. The only "animation" is the `<details>` marker rotation (single 200ms
    transition) and the install button hover (single 150ms color transition).

14. **Pointer cancellation (SC 2.5.2):** Native button + anchor + summary semantics —
    browsers handle pointer cancellation correctly out of the box. No custom click
    handlers that fire on `pointerdown`.

## Microcopy & Edge Cases

### Already-installed users (D-LAND-08)

When `window.matchMedia('(display-mode: standalone)').matches === true` OR
`window.navigator.standalone === true`, the inline `<script>` removes the entire
`#install-cta` element on page load. The landing then shows: hero visual + h1 + value
paragraph + (nothing where the CTA was) + screenshot + FAQ + iOS honesty + footer.

**Visual note:** The hero block's `margin-bottom` (handled by the `.install-cta`'s
`margin: 2rem 0 3rem` being absent) collapses, so the screenshot section sits closer
to the hero. This is acceptable — installed users don't need the CTA-induced spacing.
[Claude's Discretion — alternative is to add a `margin-bottom: 3rem` to `.hero` to
preserve the gap; planner chooses based on visual review]

### Firefox / Edge desktop (no `beforeinstallprompt`, no iOS)

After 30 seconds with no `beforeinstallprompt` event fired AND iOS detection returning
false, the universal fallback microcopy reveals itself:
`Works in any modern browser. Install for offline use.`

This text replaces the missing install button in the visual hierarchy — the user
still sees the `.open-app-link` ("Open Soundly") which works in any browser.

### Dark mode preview

The dark-mode palette swap is automatic via `@media (prefers-color-scheme: dark)`.
A user with dark system theme sees:
- Deep forest background (`#2a2f26`)
- Warm sand text (`#d4cbbe`)
- Lifted sage headings (`#a4b29a`)
- Lifted accent for install confirmation (`#d49075`)
- All other relationships preserved

**Brand fidelity check:** The OG image (`og-image-v1.png`) was rendered for light
mode (warm cream background). In dark mode it appears on a deep-forest page — the
contrast is still acceptable (the image has dark text on cream, which now floats on
a darker page surface). If needed, the planner may add a `<picture>` element with a
dark-mode variant of the hero asset, but for v1 the single asset suffices. [Claude's
Discretion — defer dark hero variant to v2.1]
